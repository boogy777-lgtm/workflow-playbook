# Автономная команда

Этот протокол дополняет `PLAYBOOK.md`. В репозитории-источнике основной файл называется `workflow-playbook.md`. Полномочия определяет раздел Execution policy основного файла. Протокол описывает работу активной сессии агента. Он сам не запускает процессы, модели или GitHub Actions.

## Что взято из ArtCraft

Основа сравнения: открытые инструкции [CADCraft на проверенной ревизии](https://github.com/storytold/cadcraft/blob/d3ae8a6af0b76185e33f6dc2735679fa5c2be77c/AGENTS.md). Проверено 2026-10-27. SHA содержимого файла: `cd6de23e3e06016cefa7ff2172033dfe604a84bb`.

В открытом файле указаны продолжение работы по плану, отдельные области записи агентов, отдельные каталоги сборки, проверка результата UI и единый набор проверок перед фиксацией изменения. Полный протокол проекта находится в локальном `plan/`, который исключён из Git. Его содержание здесь не воспроизводится. Репозиторий `storytold/craftrules`, на который ссылается CADCraft, не удалось получить через доступное соединение.

Дальше описана наша адаптация. Это не заявление о внутренней реализации команды ArtCraft. Автоматический push в main из правил CADCraft заменён границей поставки из Execution policy. План и обезличенные отчёты должны переживать сессию; приватные данные и секреты в Git не добавляют.

## Роли и границы

| Роль | Ответственность | Граница записи |
| --- | --- | --- |
| Координатор | Декомпозиция, зависимости, назначения, интеграция, связь с пользователем | Общие записи проекта и интеграционная ветка |
| Исполнитель | Реализация одного контракта задачи и проверки своего изменения | Только выданные пути |
| Ревьюер | Контракт, логика, дефекты, архитектура, достаточность проверок | Только собственный отчёт; продукт читает |
| Проверяющий | Воспроизведение сценария и запуск проверок интегрированного результата | Только собственные отчёты и изолированные результаты сборки |

Роли не означают фиксированное число процессов. Для маленькой задачи достаточно исполнителя и отдельного ревьюера, а проверки запускает координатор. Для независимых крупных задач добавляют исполнителей. Если хост не поддерживает субагентов, работайте последовательно и явно укажите отсутствие независимого ревью. Не изображайте несколько агентов ответами одной модели.

Только координатор изменяет `todo.md`, `REQUIREMENTS.md`, `MILESTONES.md` и `LEARNINGS.md`. Рабочий агент возвращает отчёт. Агент не назначает себе следующую задачу, не расширяет свою область записи и не запускает вложенную команду без назначения координатора.

## Контракт задачи

`todo.md` является единственным источником статусов. Отчёты содержат доказательства, но не создают вторую очередь. Для обычной задачи используйте компактную карточку. Для опечатки достаточно строки задачи с результатом проверки.

```text
ID: T-010
Goal / requirement: <наблюдаемое изменение и ссылка на требование>
State: pending
Depends: <ID задач; none для корневой задачи>
Owner / attempt: <worker-id; номер попытки>
Base / workspace: <commit; worktree или общая рабочая папка>
Read: <контракты и исходники для чтения>
Write: <исчерпывающие пути записи; none для чтения>
Accept: <сценарий, ожидаемый результат и запрещённые регрессии>
Checks: <команды, среда, критерии успеха>
Evidence: <commit, отчёты, результаты команд и ревью>
Acceptance: not_required | pending | accepted
Retries: 0
Progress / next: <время, полученный результат, следующее действие>
```

Перед реализацией нового случая, нового класса или исправления дефекта добавьте 2–4 строки по PLATFORM ARCHITECTURE RULES v3.1. Для опечатки или однострочного изменения без затронутого класса этот блок не нужен.

- `Class`: критерий принадлежности, близкий случай вне класса, пути механизма.
- `Inv`: гарантия для каждого случая и проверка гарантии.
- `N+1`: места изменения для следующего случая; для дефекта также другие места той же ошибки и защита от повторения.

Считайте `R` независимыми правилами, `I` проверяемыми инвариантами, `K_core` доменным знанием в ядре, `C_unrelated` связностью независимых компонентов, `E` местами расширения кроме самого нового случая. Проверка: `ΔR <= ΔI`; если `ΔI = 0`, требуйте `ΔK_core = 0`, `ΔC_unrelated = 0` и минимального `E`. Пропуск любого обязательного места из `E` должен ломать сборку или содержательную проверку. Новый механизм обоснуйте новым инвариантом.

## Статусы и допуск к завершению

| Статус | Условие |
| --- | --- |
| `pending` | Задача разобрана, но её зависимости или контракт ещё не готовы |
| `ready` | Контракт полон, зависимости завершены, область записи доступна |
| `running` | Координатор выдал задачу одному действующему исполнителю |
| `review` | Кандидат зафиксирован; ревьюер проверяет конкретную ревизию |
| `verify` | Замечания устранены; координатор проверяет интегрированную ревизию |
| `done` | Критерии выполнены, обязательное ревью разрешено, проверки интеграции прошли, доказательства записаны |
| `blocked` | Известный дефект, конфликт или отсутствующая возможность мешает завершению |
| `awaiting_user` | Для следующего действия нужна конкретная нерешённая воля пользователя |

Основной путь: `pending → ready → running → review → verify → done`. Замечание возвращает задачу в `running`; ошибка проверки переводит её в `blocked`. После устранения причины координатор возвращает задачу в `ready`, сохраняя историю попыток. После любого изменения кандидата ранее выданное ревью и затронутые проверки требуют повторной оценки.

`done` означает техническое завершение. `Acceptance` хранит отдельную приёмку на целевой системе или оценку пользователя. Если следующая задача зависит от этой приёмки, явно укажите это в её контракте и не переводите её в `ready` до принятия. Иначе независимая работа продолжается. Старый статус `passed` переносите в `done` только после проверки доказательств; иначе используйте `verify`.

Если независимое ревью недоступно, по умолчанию оставьте задачу в `review` и продолжайте независимую работу. Пользователь может заранее разрешить последовательный режим без независимого ревью; тогда запишите исключение в контракт, выполните отдельный проход самопроверки и назовите ограничение в отчёте. Самопроверка не становится независимым ревью.

## Цикл координатора

1. Прочитайте текущие требования, состояние Git, статусы, отчёты и доступные возможности хоста. Не запускайте второй экземпляр уже выполняемой задачи.
2. Проверьте граф: ID уникальны, все зависимости существуют, циклов нет, у каждой задачи есть наблюдаемый критерий завершения.
3. Выберите готовые задачи. Сначала устраните риски потери данных, затем блокеры критического пути, затем ближайший работающий сквозной сценарий. Не запускайте зависимую задачу по обещанию исполнителя.
4. Проверьте запись. Совпадающие файлы, вложенные каталоги и потенциально пересекающиеся шаблоны конфликтуют. Чтение разрешено совместно. Отдельный worktree не разрешает одновременное изменение общего контракта.
5. Назначьте исполнителей в пределах доступных слотов. Выдайте каждому карточку задачи и точный формат отчёта. Зарезервируйте возможность ревью и интеграции; не заполняйте все слоты новыми реализациями, если готовые результаты ждут проверки.
6. Пока исполнители работают, координатор разбирает следующие задачи, готовит интеграцию или проверяет результаты. При отсутствии полезной работы используйте ожидание хоста, не создавайте цикл частого опроса.
7. Передайте кандидата ревьюеру, который не является его автором. Дайте ему требование, базовую ревизию, diff и критерии проверки. Просите найти опровержение корректности, а не подтвердить объяснение автора.
8. Интегрируйте принятый кандидат. Проверьте diff, исходные ограничения, отсутствие чужих правок и неожиданных зависимостей. Разрешайте конфликты по контрактам. Повторите затронутое ревью после разрешения смыслового конфликта.
9. Выполните проверки на итоговом сочетании изменений. Запишите ревизию, команды, коды выхода и среду. Обновите задачу и журнал, освободите владение и запустите следующую готовую задачу.
10. Продолжайте до согласованной границы поставки, исчерпания готовых задач или подтверждённого ограничения хоста. При блокировке всех задач выдайте один отчёт с причинами и требуемыми решениями. Не заканчивайте словами «могу продолжить», если доступна разрешённая работа.

Ограничьте число одновременно активных задач доступными слотами и возможностью проверки. Не дробите одну связанную правку между агентами ради числа агентов. Типичный поток: работающий минимальный сценарий, затем проверяемое расширение.

## Изоляция записи и сборки

Используйте отдельный worktree для каждого пишущего агента, когда это поддерживает среда. В общей рабочей папке выдавайте непересекающиеся пути. Общие манифесты, lock-файлы, схемы и публичные интерфейсы меняет один назначенный владелец. Если они нужны нескольким задачам, сначала выполните общую предпосылку или сериализуйте изменения.

Для Rust разделяйте `CARGO_TARGET_DIR`, если параллельные сборки мешают друг другу. Для других стеков разделяйте их выходные каталоги по той же причине. Это настройка среды исполнения, а не доменное знание ядра. Координатор удаляет только созданные командой временные каталоги после проверки, что они больше не используются.

Агент возвращает commit или точный diff и путь своего отчёта. Его выводы не должны зависеть от недоступного чата. Интеграцию, push и изменение общих записей выполняет только координатор.

## Формат отчёта

Храните отчёты в `evidence/<task-id>/<attempt>-<role>.md`. Не перезаписывайте чужой отчёт.

```text
Task / role / agent:
Base / candidate revision:
Outcome: candidate | changes_requested | approved | failed | blocked
Changed paths:
Observed behavior:
Checks: <команда; среда; код выхода; краткий результат>
Findings: <воспроизведение; ожидаемое; фактическое; место в коде>
Requirement / invariant coverage:
Target acceptance still needed:
Next action / blocker:
```

Для рабочего изменения ревью должно проверить три слоя: соответствие требованию, правильность логики и устойчивость общего механизма для следующего случая того же класса. Проверяющий запускает пользовательский сценарий, а не только тест автора. Изменение UI требует изображения или доступного интерактивного результата с оценкой поведения. Недоступную среду обозначайте как непроверенную.

Нельзя повышать процент готовности по числу функций, команд, тестов или строк кода. Завершение подтверждает работающий сценарий с указанной ревизией. Нельзя скрывать провал отключением теста, исключением платформы или ослаблением критерия.

## Сбой, повтор и возобновление

При сбое сохраните ошибку и диагноз по Phase 3. Две повторные попытки относятся к задаче и сохраняются при смене агента. После исчерпания попыток новый ревьюер или координатор проводит отдельную диагностику; повторный запуск допустим только после записанного нового основания. Один и тот же ход без новых данных не является новым основанием.

Назначьте интервал проверки прогресса по длительности задачи и возможностям хоста. Отсутствие результата опроса не доказывает гибель агента. При подозрении на зависание сначала запросите статус. Перед передачей владения остановите прежнего исполнителя через хост и убедитесь, что он больше не пишет. Если это подтвердить нельзя, блокируйте его область, но продолжайте независимые задачи.

Перед компакцией, завершением сессии или заменой координатора сохраните текущую ревизию, незавершённый diff, владельцев, отчёты, блокеры и следующее действие. При неожиданном обрыве новый координатор восстанавливает состояние по файлам, процессам и Git. Он сверяет фактический эффект последнего действия до его повтора. Готовую миграцию, commit, PR или внешнюю операцию не повторяют из-за потерянного сообщения об успехе.

Окончание сессии не запускает следующую. Для работы без открытого чата нужен отдельно настроенный исполнитель: например, служба или CI с моделью, полномочиями и сохраняемым состоянием. Этот репозиторий такого исполнителя не устанавливает и платные вызовы не запускает.

## Приёмочные сценарии протокола

Перед использованием в новом хосте проверьте его доступные операции и пройдите сценарии на временной ветке. Это проверка процесса, а не обещание уже выполненного испытания команды.

| Сценарий | Требуемое поведение |
| --- | --- |
| Две независимые задачи | Оба исполнителя работают; их запись и сборка изолированы |
| Два изменения одного lock-файла | Координатор назначает одного владельца или сериализует задачи |
| Рабочая ветка зелёная, интеграция красная | Задача не получает `done`; зависимые задачи не стартуют |
| Исполнитель сообщил «готово» без доказательств | Координатор возвращает кандидата на проверку |
| Смена агента после двух повторов | Счётчик сохраняется; нужна отдельная диагностика |
| Потерян ответ на создание PR | Координатор проверяет существующие PR до повтора |
| Целевой контроллер недоступен | Приёмка остаётся `pending`; независимая разработка продолжается |
| Субагентов нет | Последовательный режим раскрыт; независимое ревью не выдумано |
| Пользователь уже разрешил слияние | После обязательных проверок координатор использует прежнее разрешение |
| Разрешена только подготовка PR | Команда доставляет PR и останавливается на этой границе |
